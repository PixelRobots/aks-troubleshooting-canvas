# AKS Troubleshooting Canvas

A Pixel Robots-branded, evidence-first Kubernetes troubleshooting workspace for Copilot sessions in VS Code. Select a kubeconfig context and namespace, explore deployments, pods and recent events, and inspect pod logs and Copilot issues.

## What works

- Choose a local kubeconfig context first. Automated investigation is cluster-wide; use Manual investigation to choose a namespace, browse workloads and events, or access monitoring links. Switch clusters without changing your active kubectl context.
- The overview presents cluster checks and Copilot findings as one set, grouped by owning workloads when ownership is available (for example, Pods under Deployments/StatefulSets and Job Pods under CronJobs). Copilot findings enrich matching groups or add distinct issues, rather than creating a second list. Investigate a resource to review its evidence, suggested next steps and documentation. Filter by workload, resource or namespace without changing the underlying scan. It checks Pods, Deployments and Nodes across namespaces for selected current signals, and reads ReplicaSet and Job owner references to group related resources. It also checks selected Kubernetes Warning event reasons from the last hour for scanned resources and verified owners, matching resource UIDs and consolidating repeated events. Event messages are not included; warnings may be stale and do not confirm a cause. The event check reads at most 2,000 events and reports incomplete results if the limit is reached. Pod volume references associate related PVC and SecretProviderClass findings with their workload when unambiguous. Cluster-wide reads use Kubernetes API pagination; a failed page makes results incomplete and may reduce grouping detail. These checks are not a full cluster health assessment or AI diagnoses.
- For AKS nodes with an `Unknown` Ready condition, the overview uses the Azure CLI to check the node pool's scale-down mode and the VM scale set instance's power state. An unknown node is excluded only when both the pool uses `Deallocate` and the instance is deallocated. If verification fails, the node remains an issue and the scan is marked incomplete.
- Selecting a cluster runs read-only checks, then automatically asks Copilot to review grouped signals in the current chat. The review uses supplied evidence rather than requesting additional cluster reads and publishes evidence-backed updates in a batch. It does not independently verify causes. For more than 100 groups, Copilot reviews the first 100 and the canvas reports this limit; all findings remain visible. Opening a finding starts a focused investigation with additional local evidence. **Rescan cluster** updates checks; **Investigate again** reviews the latest grouped signals. Findings from an earlier Copilot review may remain visible after rescanning, marked by their source. Reopening the canvas does not automatically send another request.
- Cluster checks show a tick when all selected checks finish, or a warning when results are incomplete. A tick does not mean the cluster is healthy. Copilot request completion is separate; check chat for its outcome.
- Use Manual investigation to send a question to Copilot about the cluster, or inspect a resource and ask a question scoped to it. Questions are sent to the current chat; do not include secrets or sensitive logs.
- In Manual investigation, choose a namespace, filter pods and deployments, then select a workload and choose **Investigate resource**. You can also browse workload status and namespace-specific signals, recent Kubernetes events and current or previous pod logs.
- Opening an automatic finding or a resource from Manual investigation starts a focused read-only Copilot investigation and displays its completed chat response with formatted headings, lists and links to official documentation. Published findings remain available separately without duplicating the summary. Resource-specific question answers also appear there, and an earlier summary is marked while a new request is running or has failed. Grouped workload views combine equivalent cluster signals and allow affected resources to be opened; opening a child shows its own findings rather than its siblings'. Related resources include actual owners and pod volume references (PVCs and CSI SecretProviderClasses), deduplicated across scanned descendant pods, rather than a list of those pods. References do not establish a cause and may be incomplete. **Refresh investigation** reloads evidence and requests a new summary. Both views show conditions, container waiting reasons and resource-specific events. CronJobs show their schedule status separately from the scanned phases of affected pods; Pending describes pods, not the CronJob schedule. Scan signals can be older than the current resource evidence. Full logs and `kubectl describe` are displayed only when explicitly loaded; this is a targeted projection, not a complete `describe` replacement.
- Open Azure portal and monitoring documentation links, and optionally enter an HTTPS Grafana dashboard URL.
- Opt into editing with the header switch and confirmation dialog for the selected context and namespace. The only implemented change is scaling a deployment, with a separate confirmation for each action. Editing resets when the context or namespace changes.

This is an early prototype, not a replacement for the Azure portal. It does **not** yet query Container Insights, managed Prometheus or Grafana, draw historical charts, discover Azure subscriptions, or automatically discover a Grafana dashboard. Historical monitoring depends on existing sources, retention and permissions.

## Install

Requires a VS Code Copilot-harness session with [canvases enabled](https://code.visualstudio.com/docs/agents/run/canvases), Node.js, `kubectl` on the extension host, and access to a kubeconfig and cluster. Kubernetes permissions and network connectivity still apply. Checking AKS node deallocation additionally requires a signed-in Azure CLI with read access to the node resource group, AKS cluster, node pool and VM scale set instance; the check uses the subscription in the node's Azure provider ID without changing the active subscription. It also requires the AKS-managed cluster identity tags on the node resource group. The plugin runs commands locally as the current user; it does not install or configure AKS MCP.

In VS Code, use **Chat: Install Plugin from Source**, and choose the local repository folder or this repository's Git URL. Start a Copilot-harness session and ask it to open the **AKS Troubleshooting** canvas. Plugin installation and canvas availability depend on the host's supported plugin workflow; canvases are a preview feature.

For Copilot-assisted AKS investigation, optionally enable the existing [AKS MCP server](https://azure.github.io/vscode-aks-tools/features/aks-mcp-server-integration.html) or other approved tools. The canvas's own views use `kubectl`; they do not automatically call MCP tools. Selected cluster-admin contexts can be used for authorized read-only `get` and list operations; read-only limits the operations, not the credential's privileges. A least-privileged identity is recommended. MCP access levels are guardrails, not security boundaries. If an existing chat loaded older investigation instructions, start a new chat after updating the plugin.

## Safety and privacy

Read-only is the default for this canvas, not a restriction on other tools, processes or your Kubernetes credentials. Selecting edit mode does not grant privileges. Scaling takes effect immediately, can affect availability, and may be reverted by GitOps; review your deployment's current state and rollback plan first.

Selecting a cluster sends up to 100 locally generated, owner-grouped scan findings to Copilot for review and enrichment; this automatic review does not make additional cluster reads or independently verify the findings. Opening a finding or manually investigating a resource sends a focused request. The canvas reads resource status and events locally and samples up to three related pods identified by the scan, including their recent logs (up to 200 lines per container, and previous logs for restarted containers). It sends only allowlisted indicators, such as replica and restart counts, CronJob scheduling status, termination exit codes, and fixed diagnostic matches for scheduling, Key Vault and CSI mount errors, image pulls, probes and logs. For up to 10 event-indicator combinations, it also identifies matches from the same event and its reported time and count; additional combinations are reported as omitted. It does not send raw messages, log snippets, vault names, secret names or other identifiers extracted from their text. The selected resource, namespace and context are sent to Copilot. Termination and event indicators may be historical, and matches lack context; none are diagnoses. Absent or failed reads and sampling limits are reported. Manual questions are sent to Copilot when submitted. The focused request does not ask Copilot to perform further data reads. Resource events and explicitly loaded logs and descriptions are displayed locally; their raw content is not automatically included in the Copilot request. Logs and events can contain credentials or personal data. Treat cluster content as untrusted. Previously saved manual findings are not deleted by this update; they remain unencrypted under `extension-data/pixelrobots-aks-troubleshooting/` in Copilot's home directory (`COPILOT_HOME`, or `~/.copilot`). Protect access to your machine and delete individual saved files when no longer needed. Kubernetes events are ephemeral and are not monitoring history.

## Develop

The plugin source is `.plugin/plugin.json`, `extensions/aks-canvas/` and `skills/`. It uses the SDK supplied by the Copilot host and has no npm dependencies. Run:

```powershell
node --test tests\*.test.mjs
node --check extensions\aks-canvas\extension.mjs
```

Tests use fake Kubernetes calls; they do not validate live Azure connectivity. To add troubleshooting skills, create another `skills/<name>/SKILL.md` following the [Agent Skills format](https://code.visualstudio.com/docs/agent-customization/agent-skills), and test it in a host session. Never add credentials to the repository.
