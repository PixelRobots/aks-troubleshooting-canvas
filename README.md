# AKS Troubleshooting Canvas

A Pixel Robots-branded, evidence-first Kubernetes troubleshooting workspace for Copilot sessions in VS Code. Select a kubeconfig context and namespace, explore deployments, pods and recent events, and inspect pod logs and Copilot issues.

## What works

- Choose a local kubeconfig context first. Automated investigation is cluster-wide; use Manual investigation to choose a namespace, browse workloads and events, or access monitoring links. Switch clusters without changing your active kubectl context.
- The overview presents cluster checks and Copilot findings as one set, grouped by owning workloads when ownership is available (for example, Pods under Deployments/StatefulSets and Job Pods under CronJobs). Copilot findings enrich matching groups or add distinct issues, rather than creating a second list. Investigate a resource to review its evidence, suggested next steps and documentation. Filter by workload, resource or namespace without changing the underlying scan. It checks Pods, Deployments and Nodes across namespaces for selected current signals, and reads ReplicaSet and Job owner references to group related resources. It also checks selected Kubernetes Warning event reasons from the last hour for scanned resources and verified owners, matching resource UIDs and consolidating repeated events. Event messages are not included; warnings may be stale and do not confirm a cause. The event check reads at most 2,000 events and reports incomplete results if the limit is reached. Pod volume references associate related PVC and SecretProviderClass findings with their workload when unambiguous. Cluster-wide reads use Kubernetes API pagination; a failed page makes results incomplete and may reduce grouping detail. These checks are not a full cluster health assessment or AI diagnoses.
- For AKS nodes with an `Unknown` Ready condition, the overview uses the Azure CLI to check the node pool's scale-down mode and the VM scale set instance's power state. An unknown node is excluded only when both the pool uses `Deallocate` and the instance is deallocated. If verification fails, the node remains an issue and the scan is marked incomplete.
- Selecting a cluster runs read-only checks, then automatically deepens the highest-priority groups in the canvas before asking Copilot to review them. The current default is six detailed background diagnoses per review, selected by crash, mount, scheduling and probe severity; all groups still receive the summary review. The evidence collector reads current status and events for each selected owner, samples related pods and jobs, and safely projects referenced storage resources. A three-stage workflow builds an evidence map, drafts the diagnosis, and then verifies it for unsupported certainty. Incomplete-check warnings remain visible. For more than 100 groups, Copilot reviews the first 100 and the canvas reports this limit; all findings remain visible. Opening a finding starts a fresh focused investigation with additional local evidence. **Rescan cluster** updates checks; **Investigate again** reviews the latest grouped signals. Findings from an earlier Copilot review may remain visible after rescanning, marked by their source. Reopening the canvas does not automatically send another request.
- Cluster checks show a tick when all selected checks finish, or a warning when results are incomplete. A tick does not mean the cluster is healthy. Copilot review completion and errors are shown separately in the canvas.
- Use Manual investigation to converse with Copilot about the cluster or a selected resource. Conversations appear in the canvas, and subsequent questions include the recent conversation for that target. Cluster questions use the most recent scan; resource questions refresh the bounded local checks. Do not include secrets or sensitive logs in questions.
- In Manual investigation, use the visual **Resource explorer** to discover resource types, including custom resources, then search and open resource cards directly. Pods are selected by default when available; choose a namespace once and use the same browser for subsequent types. Results show kind and scope, and large result sets stop at 200 cards so the search can be refined. Availability depends on API discovery and Kubernetes permissions. Supported workload types retain detailed investigations; other types use metadata-only investigations, so their configuration, status, events and health remain unknown. Quick access to pods and deployments, namespace-specific signals, recent events and pod logs remains available.
- Opening an automatic finding or a resource starts an automatic, read-only Copilot diagnosis and displays it in the canvas, with follow-up conversation available below the report. The report is structured as a timestamped cluster header, summary, what happened, ranked hypotheses, conditional impact, remediation, and prevention. It distinguishes reported event content from independently verified configuration and does not treat 404/403 indications as proof without corroboration. “Suggested follow-ups” are clickable. Cluster-check findings appear as expandable evidence: they are expanded while an investigation is running or has failed, and collapsed when it succeeds. Incomplete-check warnings remain visible. Published findings remain available separately. Grouped workload views combine equivalent cluster signals and allow affected resources to be opened; opening a child shows its own findings rather than its siblings'. Related resources include actual owners and pod volume references (PVCs and CSI SecretProviderClasses), deduplicated across scanned descendant pods. References do not establish a cause and may be incomplete. **Refresh investigation** reloads evidence and requests a new diagnosis. CronJobs show their schedule status separately from the scanned phases of affected pods. Full logs and `kubectl describe` are displayed only when explicitly loaded.
- Open Azure portal and monitoring documentation links, and optionally enter an HTTPS Grafana dashboard URL.
- Opt into editing with the header switch and confirmation dialog for the selected context and namespace. The only implemented change is scaling a deployment, with a separate confirmation for each action. Editing resets when the context or namespace changes.

This is an early prototype, not a replacement for the Azure portal. It does **not** yet query Container Insights, managed Prometheus or Grafana, draw historical charts, discover Azure subscriptions, or automatically discover a Grafana dashboard. Historical monitoring depends on existing sources, retention and permissions.

## Install

Requires a VS Code Copilot-harness session with [canvases enabled](https://code.visualstudio.com/docs/agents/run/canvases), Node.js, `kubectl` on the extension host, and access to a kubeconfig and cluster. The in-canvas assistant uses the experimental Copilot SDK Dynamic Workflows API; availability depends on host support, account eligibility and session storage. If unavailable, the canvas reports an error instead of sending the request to the main chat. Kubernetes permissions and network connectivity still apply. Checking AKS node deallocation additionally requires a signed-in Azure CLI with read access to the node resource group, AKS cluster, node pool and VM scale set instance; the check uses the subscription in the node's Azure provider ID without changing the active subscription. It also requires the AKS-managed cluster identity tags on the node resource group. The plugin runs commands locally as the current user; it does not install or configure AKS MCP.

In VS Code, use **Chat: Install Plugin from Source**, and choose the local repository folder or this repository's Git URL. Start a Copilot-harness session and ask it to open the **AKS Troubleshooting** canvas. Plugin installation and canvas availability depend on the host's supported plugin workflow; canvases are a preview feature.

For Copilot-assisted AKS investigation, optionally enable the existing [AKS MCP server](https://azure.github.io/vscode-aks-tools/features/aks-mcp-server-integration.html) or other approved tools. The canvas's own views use `kubectl`; they do not automatically call MCP tools. Selected cluster-admin contexts can be used for authorized read-only `get` and list operations; read-only limits the operations, not the credential's privileges. A least-privileged identity is recommended. MCP access levels are guardrails, not security boundaries. If an existing chat loaded older investigation instructions, start a new chat after updating the plugin.

## Safety and privacy

Read-only is the default for this canvas, not a restriction on other tools, processes or your Kubernetes credentials. Selecting edit mode does not grant privileges. Scaling takes effect immediately, can affect availability, and may be reverted by GitOps; review your deployment's current state and rollback plan first.

Selecting a cluster sends up to 100 locally generated, owner-grouped scan findings to Copilot for review and enrichment. Opening a resource or asking a resource question reads status and events locally, samples up to three scan-related pods and their recent logs, checks up to three related PVC, SecretProviderClass or Node references, and samples up to three Jobs for a CronJob. These are bounded checks, not an autonomous mutation-capable investigation; missing reads and sampling limits are reported. Only allowlisted indicators are sent, including counts, phases, Azure provider, Key Vault and object *names* from a SecretProviderClass, and fixed diagnostic matches. Raw event messages, log snippets, credentials and secret values are never sent. Resource identifiers and user-entered questions are included. The tool-free workflow agent cannot read the cluster itself. Workflow inputs and outputs are persisted in Copilot session storage; in-canvas conversation history is kept in memory while the canvas is open, with up to ten question/answer pairs per target included in follow-ups. For metadata-only resource types, including Secrets and custom resources, the canvas requests only names and selected metadata from `kubectl` output; it does not display or send values or arbitrary specifications. Kubernetes API responses to `kubectl` can nevertheless contain complete objects. Termination and event indicators may be historical and none are diagnoses. Resource events and explicitly loaded logs and descriptions are displayed locally; their raw content is not automatically included in the Copilot request. Logs and events can contain credentials or personal data. Treat cluster content as untrusted. Previously saved manual findings remain unencrypted under `extension-data/pixelrobots-aks-troubleshooting/` in Copilot's home directory (`COPILOT_HOME`, or `~/.copilot`). Protect access to your machine. Kubernetes events are ephemeral and are not monitoring history.

## Develop

The plugin source is `.plugin/plugin.json`, `extensions/aks-canvas/` and `skills/`. It uses the SDK supplied by the Copilot host and has no npm dependencies. Run:

```powershell
node --test tests\*.test.mjs
node --check extensions\aks-canvas\extension.mjs
```

Tests use fake Kubernetes calls; they do not validate live Azure connectivity. To add troubleshooting skills, create another `skills/<name>/SKILL.md` following the [Agent Skills format](https://code.visualstudio.com/docs/agent-customization/agent-skills), and test it in a host session. Never add credentials to the repository.
